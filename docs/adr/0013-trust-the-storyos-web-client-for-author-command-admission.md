# Trust the StoryOS Web Client for Author Command Admission

Release 1 includes only the exact controlled StoryOS Web Client build named by its immutable asset set, accepted client-contract and security-policy identities, and current protected Client Session Binding generation in the trusted computing boundary for author-owned commands. Rendered or imported content, model, Tool, MCP, or App output, browser extensions, third-party scripts, browser-local caches, journals, and projections are not part of that trusted claim.

The StoryOS Server derives the authenticated User and exact existing or prospective Project Scope and binds the protected client session, accepted client-contract and security-policy identities, applicable Editor Session and writer generation, action class, exact command digest, targets, expected Heads, nonce, idempotency record, lifetime, and unique terminal settlement in one `AuthorCommandAdmission`. This preserves a responsive browser-first editor while proving only an exact protected-client submission, not one physical human gesture, trusted display, user presence, or user verification; stronger transaction confirmation requires a separately trusted display and confirmation surface outside the selected Release 1 boundary.

An Acceptance request refused before Admission retains a durable, bounded, sanitized `Pre-Admission Refusal Record`, as required by the [Admission failure contract](../foundation/author-command-admission.md#7-positive-failure-duplicate-and-recovery-evidence). It creates no Admission, Command, Acceptance Receipt, nonce consumption, or Core effect. Where current authorization permits disclosure, the author can inspect the typed refusal after reload and distinguish loss of writer eligibility from an invalid challenge. Unproved identity or Scope permits only a safe generic error. Session refusal leaves Proposal validity unchanged and disables Acceptance for the ineligible session.

After the author restores writer eligibility, Acceptance requires a fresh explicit command and challenge; the client does not automatically apply the earlier intent. A first Acceptance attempt that enters Core always produces its typed Receipt, including a domain refusal. An uncertain post-admission outcome requires reconciliation against the original command instead of a new Acceptance. This keeps failure inspectable without treating every rejected HTTP request as a domain attempt or changing all refusals to HTTP 200.

`storyos.acceptance-refusal.fixed-fields.v1` binds one immutable record to one existing scoped Challenge key. Record attribution requires the exact command digest, protected client binding and profile, an in-Scope Proposal, and no Admission or settled outcome. The refusal transaction rechecks these facts under the same Challenge/idempotency locks after the command transaction rolls back. Unknown bindings retain only a safe protocol error. Known bindings can retain an invalid-challenge reason, including nonce failure or expiry. A retained key cannot later enter Core; a new explicit attempt requires a new key and Challenge.

The record contains UUID identities, closed reason and boundary values, accepted contract/profile identities, and audit time. It contains no body, nonce, session handle, or foreign identity. The existing `storyos.project-command-challenge-rate.fixed-window.v1` bounds new Challenge ingress to ten per sixty-second window per User/Project/session generation; one record per key bounds write amplification, not total storage across time or generations. Records remain in the existing Operational Evidence Floor, with Project Archive and physical restore support. This adopts no deletion interval or global capacity promise. The versioned `getProposal` query returns at most the latest safe refusal, under current Scope, as historical evidence separate from content validity and current writer eligibility. Earlier records remain in the archive. SQL fixes the accepted identity set; a later identity change requires the storage-owned activation path.
