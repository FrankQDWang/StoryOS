# Static cost inventory for the Chinese long-form baseline

Source snapshot: `479224809cdaae997cda51cb8853e3fafa242b65`. Research date: 2026-10-05. Product files have not changed in this branch. This is a source audit, not a wall-clock benchmark. The scale-envelope report owns the complete four-scale operation table. The measured-plan section below explains selected SQL observations; it does not turn planner choices into stable application bounds.

## Findings in impact order

1. **Saving one Chapter can scan all prose for the visible count.** The save application path targets one Chapter, but its actual SQL plans can read Project-wide history or join candidates. In addition, `ManuscriptStatisticsPanel` refreshes on `saveState`, Current Chapter, and tree revision changes. Statistics load every live Chapter payload and count every scalar. A small response does not imply a small database read.
2. **Readable-export admission contains a quadratic Chapter lookup.** Each tree Chapter searches the whole ordered Chapter-fact vector from its start. At 1,500 Chapters this is 1,125,750 Chapter-ID comparisons when both vectors contain the same Chapters, in any permutation. This work occurs before asynchronous export settlement.
3. **Ordinary local editing still reads retained journal history.** The bounded working-journal query calls the Acceptance Journal reader, which reads all partition intents/groups and all database transport capsules/attempts. The latter also performs repeated scans for each explicit decision. This conflicts with the lifetime-read intent in `docs/adr/0036-bound-active-journal-reads-with-retained-history.md:11`; the bounded working index alone does not meet that intent.
4. **Chapter reorder and deletion read all live Chapter identities.** Reorder locks all live Chapters before it selects siblings. Deletion reads all live Chapters to choose the next Current Chapter. These paths grow with book structure even if only one node changes.
5. **Proposal inspection, Acceptance, and recovery have additional products of input sizes.** These include location rendering, candidate journal reconstruction per pending Operation, Block-by-Operation matching, and comparison cleanup. They depend on Proposal/history/Block shape; a fresh 1,500-Chapter book with one small Proposal does not exercise their worst cases.

## Variables and interpretation

- `N`: total live manuscript text; `C`: live Chapters; `V`: live Volumes.
- `n`: text in the affected Chapter; `B`: Blocks in that Chapter; `L`: compared Block/slice text; `D`: edit distance; `E`: diff edit groups.
- `S`: Chapters in one Volume; `S_all`: its live and removed Chapter rows.
- `P`: retained/displayed Proposals; `Q`: Operations in a Proposal or displayed pending set; `R`: returned Proposal locations.
- `H`: retained author/session history. For browser analysis, `H_p` is all intents/groups in the current partition, `H_t` is all capsules/attempts in the same journal database, `H_w` is the working set, and `A` is explicit Acceptance/Rejection records. `J` is journal partitions.
- Working-journal arrays are capped at 2,400, and edit batches at 240 units/primitives: `apps/web/src/journal-working-set.ts:5`, `apps/web/src/local-edit-journal.ts:55`. The Acceptance reader checks `A <= 2400` **after** unbounded reads. These caps do not bound retained `H_p`, `H_t`, or manuscript size.
- Costs below separate explicit application iteration from planner-dependent SQL. Indexed point reads are not labeled constant-time physical I/O. A correlated SQL subquery is not automatically an `O(C²)` execution plan.

## Correctness findings that affect this cost envelope

The directory queries sort the output `tree_order::text` column (`manuscript_tree.rs:73-84`, `:91-103`) and renumber that order as public sibling ranks (`:112-129`). This yields text order across decimal widths. The Web uses those ranks for move and rename commands, while mutation queries use numeric storage order. Thus it is not only a visual issue: submitted ranks can change persistent order (`update_chapter.rs:155-160`, `update_volume.rs:141-145`). Readable export uses the same tree and pins its order (`readable_export.rs:274-296`). These correctness findings belong beside the measurements; a successful command response alone does not prove intended adjacent movement.

The default run's ordinary recovery and Unicode reload pass, but the later reload after structural actions and export enters `needs_attention` with a read-only editor at every scale. Its partial cost must not be presented as successful recovery cost. The exact source-backed candidate and later diagnostic evidence are recorded in the main report. This audit does not infer text corruption from that state.

## SQL interpretation and retained storage

- Whole-book search/statistics SQL has one ordered `array_agg` member subquery per Chapter (`crates/storyos-adapter-postgres/src/manuscript_search.rs:88`). Indexed access can produce total member work proportional to `sum(B_i)` plus lookups/order. A repeated sequential subplan can cost much more. Inspect actual `loops`, rows, filters, and buffers; SQL statement count alone cannot select between them.
- Tree, membership, search, and structure queries contain `ORDER BY`. An ordered index can avoid a Sort; an explicit comparison Sort generally adds a log factor. This report lists required order and explicit application sorts, not invented PostgreSQL node costs.
- Save membership is **two batched inserts**, not two statements per Block (`crates/storyos-adapter-postgres/src/manuscript_block.rs:311`). Its row count and bytes still scale with `B`. Full Chapter revisions retain new payload bytes and memberships, so repeated saves grow history roughly with the sum of changed Chapter sizes, not with every Chapter in the book.
- Chapter reorder's first UPDATE lacks a removal filter (`crates/storyos-adapter-postgres/src/update_chapter/sibling_order.rs:11`): repeated create/delete history can increase affected rows while live `C` is unchanged. The million-ID fallback at `:42` changes statement count; it is outside the 1,500-Chapter workload.
- The Undo frontier's anti-join and descending `LIMIT 1` can inspect retained history before finding an uncompensated entry (`crates/storyos-adapter-postgres/src/undo_frontier.rs:119`). A one-row result does not prove one examined row.
- Statistics response bytes can remain nearly constant while SQL-to-Server text grows as `N`. Export download must transfer `N`; Chapter/session responses grow with `n`; tree responses grow with `C+V`. These are different boundaries and must have separate byte counters.

The inventory follows owning product source, not historical issue claims. No product changes, new tests, or benchmarks were run for this static pass.

This is a scoped source inventory, not a proof that every possible repository path has a tight complexity bound. The synthetic four-scale corpus controls `N` and `C`; it does not by itself vary long-lived `H`, dense `P/Q`, one giant `L`, or dense single-Chapter `B`.
